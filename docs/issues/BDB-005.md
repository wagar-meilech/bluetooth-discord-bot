# Prove native macOS Bluetooth receiver feasibility

Parent spec: https://github.com/wagar-meilech/bluetooth-discord-bot/issues/2
Local ID: BDB-005
Depends on: None

## Purpose and scope

Investigate the highest-risk native receiver path first using public IOBluetooth APIs and reusable Rust bindings. Preserve the host Bluetooth stack and other devices. Do not substitute AirPlay, external receivers, Linux, private APIs, radio resets, or unpairing.

Begin with a reversible runtime probe for public service publication and incoming AVDTP L2CAP registration. Verify the actual published PSM; a reassigned PSM is not proof of a compatible receiver. Registration is only a prerequisite: actual phone connection, protocol negotiation and live audio remain separate requirements. Extend only when earlier evidence supports it.

## Acceptance criteria

- Record local OS/SDK/toolchain and the exact public APIs exercised.
- A runnable Rust probe cleans up only its own registrations on normal/error exits; unsupported or conflicting ownership fails clearly.
- Record actual runtime results separately from compile/static evidence.
- Establish built-in-radio reception of a real intended phone's live audio, or report a specific required-path failure with evidence and next options.
- No bot-caused disruption of the host's normal Bluetooth peripherals, speaker/headset microphone use, or source stream.
- Keep the native macOS capability gate unpassed until live receiver behavior is observed; do not claim registration or bindings implement A2DP.

## Test seam and validation

Use the approved installed-system/hardware seam for OS capability evidence. Tests for any bridge-session behavior use the approved public control/audio-input seam with OS endpoints substituted; do not add tests for thin FFI wrappers or vendor internals. Follow one red/green slice at a time if session logic is introduced.

Record commands, exit status and bounded diagnostic output. Manual pairing/consent and real-device evidence must be attributed, never fabricated.

## Current local evidence

The minimal Rust probe builds, public API/controller preflight succeeded, and the documented in-memory attribute parser accepted the six bundled fields and PSM 0x19 without publishing. The single transient SDP-publication attempt returned nil (probe exit 5; empty stderr), without an owned record to remove. No live audio or coexistence test has passed. See [the durable result and commands](../feasibility/macos-receiver.md). The local prerequisite failure is undiagnosed; it does not establish universal Mac impossibility.

[Draft PR #10](https://github.com/wagar-meilech/bluetooth-discord-bot/pull/10) contains

would require a new decision; no fallback has been accepted.

## Controlled follow-up

The same unchanged binary outside the tool sandbox publishes/removes a generic
custom-UUID L2CAP service at `0x1001`, but changing only the requested PSM to
AVDTP `0x19` returns no record. Bare key formatting did not repair the AudioSink
case. CoreBluetooth class authorization is allowed; no new permission request
was made. This isolates requested-PSM-dependent high-level publication/record
materialization, without identifying a service owner or proving universal Mac
impossibility. [Full diagnosis and evidence](../feasibility/macos-sdp-diagnosis.md).

The standard sink profile mandates the assigned AVDTP PSM, so the generic dynamic
port does not replace the required path. Windows feasibility is advancing
independently; the full two-platform gate still depends on resolving this ticket.

## Controlled diagnosis follow-up

The class-only context getter reports own bundle identity/purpose and
CoreBluetooth authorization 3 outside the tool sandbox; this does not certify
IOBluetooth permissions. Bare-decimal publisher keys alone did not resolve nil.
A custom-UUID generic L2CAP control returned and removed a record on dynamic PSM
0x1001. Changing only its requested PSM to0x19 returned no record. A matched pair
on one unchanged binary confirmed that distinction. The exact system cause and
channel ownership remain unclassified; no live receiver or coexistence proof was
obtained. See [the diagnosis and strict paired evidence](../feasibility/macos-sdp-diagnosis.md).

## Lifecycle and handle follow-up

The one-second pre-publication main-run-loop variation did not repair assigned PSM0x19. After correcting and explicitly invalidating one misdispatched dynamic-control attempt, valid same-binary typed/plain requested-handle pairs both returned owned records on dynamic0x1001 and nil on assigned0x19. A new semantic payload guard checks the actual selected fixture's PSM/handle before any publication. See [the recorded comparisons and limits](../feasibility/macos-sdp-lifecycle.md). This does not prove universal Mac impossibility or complete live reception.

## iPhone preparation and outbound signaling diagnostic

The explicit public OS pairing panel returned modal success, but its immediate
selected result reported unpaired; a fresh inventory later grew from 14 to 15
paired entries. The operator reports the Mac in iPhone My Devices as Not Connected.
These observations alone do not correlate the selected phone in the Mac inventory.
A reviewed outbound DISCOVER helper uses an operator picker, fresh paired identity
matching, disconnected-device precondition, and an explicitly new owned channel
only. Its first installed-system run stopped at identity matching before any
connection. Offline known-spec packet replay and build evidence remain separate
from native signaling or live audio. See [preparation and connection evidence](../feasibility/macos-iphone-connection.md).
